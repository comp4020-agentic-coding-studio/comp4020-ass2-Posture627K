## Naming a state vs. representing change

Most notations are good at **naming** something: a state, a pitch, a value.

Few are built, from the ground up, to represent **a state becoming another
state** — inside the notation itself, not described around it.

  <div class="deck-contrast-box">

```notes
No course-specific notation yet. The contrast is the whole point: naming a
state is easy, representing a transition inside the sign itself is rare.
```

## Case 1 — a traffic light

<div class="deck-signal">
  <div class="deck-signal-lamps">
    <span class="deck-lamp deck-lamp--red deck-lamp--lit"></span>
    <span class="deck-lamp deck-lamp--amber"></span>
    <span class="deck-lamp deck-lamp--green"></span>
  </div>
  <p class="deck-signal-rule">
    Names three states — red, amber, green. The transition rule lives in the
    electronics behind the light, not in the sign itself.
  </p>
</div>

Look only at the sign. You cannot tell what comes next.

```notes
Weakest case: the sequencing is entirely external. Ask: what does the
signal tell you now, and what does it fail to tell you about what happens
next? Good opener — it's the most obviously "outside the sign" case.
```

## Case 2 — musical notation

<div class="deck-sequence">
  <span class="deck-note deck-note--h2" />
  <span class="deck-note deck-note--h3" />
  <span class="deck-note deck-note--h1" />
  <span class="deck-note deck-note--h4" />
  <span class="deck-note deck-note--h2" />
</div>

Names a pitch and a duration, read left to right as time. But a crescendo, a
rubato, a held breath — most of what happens *between* marks is written
beside the notation, not as a state the notation itself transforms through.

```notes
Abstract marks stand in for notes — don't reproduce real sheet music. Ask:
does the notation represent the change itself, or tell a performer what
sequence to produce?
```

## Case 3 — a state machine

<div class="deck-chain">
  <span class="deck-chain-node">A</span>
  <span class="deck-chain-arrow">→</span>
  <span class="deck-chain-node">B</span>
  <span class="deck-chain-arrow">→</span>
  <span class="deck-chain-node">C</span>
</div>

Better again: the transitions are drawn explicitly, as arrows between
states. But the rule for each transition still sits *between* the symbols —
nothing inside "A" itself says it is about to become "B".

```notes
Keep this generic — do not connect it to trigrams yet. The teaching point:
a state machine improves on the traffic light because transitions are
explicit, but the transition rule still lives between states, not inside
the state symbol itself.
```

## Case 4 — binary code

<div class="deck-chain">
  <span class="deck-chain-node">0</span>
  <span class="deck-chain-arrow">→</span>
  <span class="deck-chain-node">1</span>
</div>

Names a single two-valued unit. But nothing in "0" or in "1" tells you it is
about to change, or into what — flipping happens *to* the bit, from outside
it.

```notes
Don't bring in Leibniz, the Yijing, or week 11 material here — this is
purely the bit as a two-valued unit. That connection is made properly much
later in the course.
```

## What these cases still lack

| System | What it names | Where the transition rule lives |
|---|---|---|
| Traffic light | three states | the electronics behind the light |
| Musical notation | a pitch and a duration | mostly an instruction to the performer |
| State machine | discrete states | the arrow between them, not the states |
| Binary code | a two-valued unit | outside the bit — flipping happens to it |

> All four name a state clearly. None of them notate the transition itself.

```notes
Let the table do the work — don't re-narrate every row. The one line that
matters: none of these four notate the transition itself.
```
